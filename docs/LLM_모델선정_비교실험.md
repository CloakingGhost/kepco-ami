실제 DB에 있는 **위험 데모 이벤트**(A-L-60 충북식당, 2026-07-02 02:15)를 그대로 썼다.

| 필드 | 값 |
|---|---|

| 계약전력 | 45 kW |
| 안전등급 | 위험 |
| 발동규칙 | KEC 212.3 산업용 배선차단기 — 계약전력 130%가 60분 지속 |

### 2-2. 라운드별 프롬프트 차이

라운드마다 프롬프트 길이를 바꿔가며 테스트했다. **모델 간 비교는 같은 라운드 안에서만 유효하다.**

| 라운드 | 시스템 프롬프트 | 사용자 입력 | max_tokens | 목적 |
|---|---|---|---|---|
| **1차** | 전체판(절대규칙 4개 + 필드별 작성 지침 + `emergency_report` 포함) | 위 이벤트 8필드 JSON | 700 | 최종 형태로 바로 테스트 |
| **2차** | 축약판(2문장 + JSON 형식 지정, `owner_sms`/`admin_note`만) | 위 이벤트 7필드 JSON | 500 | 되는 모델을 빠르게 선별 |
| **3차** | 축약판 + 문장 수/존댓말 지침 추가 | 2차와 동일 | 600 (추론형은 2000) | 워밍업 후 지연시간 재측정 |

**1차 시스템 프롬프트의 절대 규칙 4개** (실제 구현 `narrate.SYSTEM_PROMPT`에 그대로 반영됨):

1. 입력으로 받은 숫자만 사용 — 새로 만들거나 계산해서 쓰지 말 것
2. 화재·누전·아크가 발생했다고 단정하지 말 것 (패턴 이상만 감지하며 사고 여부는 모름)
3. 원인을 추정하지 말 것 ("냉장고 고장으로 보입니다" 류 금지)
4. JSON만 출력 — `{"owner_sms": ..., "admin_note": ..., "emergency_report": ...}`

### 2-3. 판정 기준

1. **추론 가능 여부** — 호출이 200으로 돌아오는가
2. **형식** — JSON으로 파싱 가능한가 (코드블록 감싸기는 허용, 파서가 벗겨냄)
3. **언어/문체** — 한국어 존댓말 문장이 나오는가
4. **수치 정확성** — 입력에 없는 숫자를 지어내지 않는가
5. **지연시간** — 화면에서 버튼 눌러 기다릴 만한가 (목표 10초 이내)

### 3-1. 채택 모델 실제 출력 (3차, 2회차)

```json
{
  "owner_sms": "충북식당 점주님, 현재 전력 사용량이 계약 전력의 130%를 초과하고 있습니다. 안전 등급이 위험으로 표시되었으므로, 전력 사용량을 점검해 주시기 바랍니다.",
  "admin_note": "KEC 212.3 산업용 배선차단기 기준에 따라 계약전력 130%가 60분 지속된 것으로 확인됨. 점검 필요."
}
```

### 3-2. 차선 모델 실제 출력 (3차, 2회차)

```json
{
  "owner_sms": "충북식당 점주님, 2026-07-02 02:15분 기준 전력 사용량이 임계치 14.63kWh를 초과한 18.95kWh로 관측되었습니다. 전기 안전을 위해 확인 부탁드립니다.",
  "admin_note": "계약전력 45kW의 130% 초과 상태가 60분 지속되어 18.95kWh가 관측됨."
}
```

**차이**: gemma는 관측/임계 수치를 문장에 직접 넣는 반면 mistral-nemotron은 비율(130%) 중심으로 쓴다.
수치 인용이 더 필요하면 프롬프트에서 "관측값과 임계값을 반드시 포함"을 명시하면 되고, 실제 구현
(`narrate.SYSTEM_PROMPT`)에는 그 지침을 넣어 두었다.

### 3-3. 탈락 사유 상세

- **`nemotron-3.5-lightning-30b-a3b`**: 추론형(reasoning) 모델이라 `<thinking>` 성격의 내부 서술이
  응답 본문에 그대로 나온다. 1차(max_tokens=700)에서는 그 서술만으로 토큰이 소진돼 JSON이 아예
  안 나왔고, 3차에서 2000으로 늘려도 64초가 걸렸다. 파싱으로 뒷부분만 건질 수는 있으나 지연시간이
  화면용으로 부적합하다.
- **`openai/gpt-oss-20b`**: `{"owner_sms":"2026-07-02 02:15 45 18.95 14.63", ...}`처럼 숫자만 나열했다.
  프롬프트를 늘리면 개선될 여지는 있으나, 같은 조건에서 다른 모델이 바로 성공했으므로 더 파지 않았다.

## 4. 한계 — 이 실험이 보장하지 않는 것

이 표를 "모델 성능 벤치마크"로 읽으면 안 된다.

1. **표본이 이벤트 1건, 호출 1~2회다.** 지연시간은 재현될 가능성이 높지만(2회차가 안정적),
   품질은 이 한 건에서 관찰한 것일 뿐 통계적 비교가 아니다.
2. **품질 판정이 주관적이다.** 한국어 자연스러움에 점수 체계를 두지 않았고, 사람이 읽고 판단했다.
   다만 **수치 정확성만은 자동 검증 가능**하며, 실제 구현에서는 매 호출마다
   `narrate.verify_numbers()`가 생성문의 숫자를 입력값과 대조한다(이게 이 계층을 채택한 핵심 근거).
3. **404/503은 모델 자체의 문제가 아닐 수 있다.** 이 API 키의 접근 권한·리전·순간 혼잡에 따라
   달라질 수 있으므로, 다른 키로는 결과가 다를 수 있다.
4. **콜드스타트 영향이 크다.** gemma-4-31b-it는 첫 호출 75.9초 → 세 번째 12.8초로 6배 차이가 났다.
   운영에서 호출 빈도가 낮으면 매번 콜드스타트를 맞을 수 있다는 뜻이므로, 채택 모델의 2.8초도
   "항상 2.8초"로 약속할 수는 없다.
5. **프롬프트가 라운드마다 달랐다.** 라운드를 가로지르는 지연시간 비교(예: 1차 11.2s vs 3차 64.4s)는
   max_tokens 차이가 섞여 있어 그대로 비교하면 안 된다.

## 5. 운영 시 유의

- 키가 없으면(`NVIDIA_API_KEY` 미설정) `POST /api/anomalies/explain`만 503을 반환하고 나머지 API는
  정상 동작한다 — 설명 계층은 부가 기능이므로 서비스 전체를 막지 않는다.
- 모델 교체는 `.env`의 `NVIDIA_MODEL` 한 줄로 가능하다(기본값은 `config.py` 참고).
- 원격 서버에도 `NVIDIA_API_KEY`가 있어야 이 엔드포인트가 동작한다. 서버 `.env`는 git에 없으므로
  배포 시 별도로 넣어야 한다.

## 6. 재점검 (2026-09-10) — 채택 모델이 죽었다

### 6-1. 증상

운영 로그에 `POST /api/anomalies/explain` **502**가 반복됐다. 502는 "외부 모델이 전부 실패했고
캐시에도 없음"(`NarrationUnavailable`)을 뜻한다.

### 6-2. 같은 프롬프트·같은 키로 전수 재호출한 결과

| 모델 | 2026-09-09 | 2026-09-10 | 판정 |
|---|---|---|---|
| `mistralai/mistral-nemotron` (구 채택) | 2.8초 | **120초 초과 무응답 / 예비 키로는 HTTP 500** | **사망** |
| `nvidia/nemotron-3-super-120b-a12b` | 64.4초(탈락) | **23.6 / 28.8 / 47.9초**, 한국어 JSON 정상 | **신규 채택** |
| `openai/gpt-oss-20b` | 문장 미생성(탈락) | 41.9초, 정상 | 예비 후보 |
| `google/gemma-4-31b-it` | 12.8초 | 57.1초, 정상(품질 가장 안정적) | 대체 유지 |
| 나머지 9종 | 404 | 404 (동일) | — |

**호출 한도 문제가 아니다.** 429도 rate-limit 헤더도 없었고, 같은 키로 gemma는 정상 응답했다.
호스팅 측 모델 상태 문제다. 4절 4항("항상 2.8초로 약속할 수 없다")이 그대로 현실이 된 사례다.

### 6-3. 같이 드러난 자체 버그 — `max_tokens` 절단

`max_tokens=1400`이 응답을 중간에 잘라 **JSON 파싱 자체가 실패**하고 있었다. 실측 소비량은
`nemotron-3-super` 1685~1744 토큰, `gpt-oss-20b` 1367 토큰이다. 2400으로 올리자 두 모델 모두
정상 파싱됐다 — 즉 9/9 실험에서 이 둘이 "탈락"한 사유 중 일부는 **모델이 아니라 우리 설정**이었다.

### 6-4. 조치

1. 1순위 모델을 `nvidia/nemotron-3-super-120b-a12b`로 교체, 죽은 모델은 후보에서 제거.
2. `max_tokens` 1400 → 2400.
3. 타임아웃을 모델별 고정(10초/14초)에서 **전체 예산 공유**로 변경. 1순위가 404로 0.2초 만에
   죽는 날 대체 모델이 남은 예산을 다 쓸 수 있게 된다.
4. **생성을 요청과 분리하고 결과를 DB에 저장**(`anomaly_narrations` 테이블).
   살아 있는 모델이 전부 24~57초라, 요청을 붙잡고 기다리면 프록시(30초)가 먼저 끊어 사용자는
   결국 에러를 본다. 그래서 요청은 즉시 `pending`으로 응답하고, 생성은 서버 백그라운드에서
   예산 180초(`JOB_BUDGET_SEC`)로 돌리며, 완료되면 DB에 저장한다. 화면은 상태 조회로 완료를
   확인하고, 한 번 만든 분석은 이후 DB에서 즉시 읽는다. 외부 모델 실패도 HTTP 에러가 아니라
   `status='failed'`와 "다시 요청해 주세요" 안내로 전달한다.

   > 처음에는 이벤트 설명을 **미리 생성해 캐시 파일에 채워 두는** 방식(7월 사건 18건)으로
   > 막았다가 되돌렸다. 요청하지 않은 분석에 외부 API를 쓰는 건 자원 낭비이고, "저장된 분석"은
   > 누군가 실제로 요청해 AI가 만든 결과여야 한다는 판단이다. 사전 생성 스크립트와 캐시 파일은
   > 삭제했다.

### 6-5. 교훈

외부 호스팅 모델은 **가용성 자체가 변수**다. 이 프로젝트가 탐지·판정을 규칙으로 두고 LLM을
설명에만 쓴 이유가 여기서 다시 확인된다 — 모델이 죽어도 **위험/주의 판정은 그대로 동작했고**,
사라진 것은 설명 문장뿐이었다.
