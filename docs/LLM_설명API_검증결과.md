## 1. 배포 — API 키 취급

키 값이 대화 로그·터미널 출력 어디에도 남지 않도록 처리했다.

1. 서버 `.env`에 이미 있는 **키 이름만** 조회해 NVIDIA 키가 없음을 확인(값 미출력)
2. 로컬 `.env`에서 `grep '^NVIDIA_'`로 **두 줄만** 별도 파일에 추출 — 화면에는 줄 수와 키 이름만 표시
3. `scp`로 파일 대 파일 전송 (내용이 중간에 노출되지 않음)
4. 서버에서 기존 `.env`를 `.env.bak`으로 백업한 뒤 **덧붙이기**(전체 덮어쓰기 금지)
5. 전송용 임시 파일은 `shred -u`로 삭제, 로컬 임시 파일도 삭제
6. `.env` 권한 `600`(root 전용) 확인

**전체 덮어쓰기를 하지 않은 이유**: 서버 `.env`에는 그 서버 전용 `DB_PASSWORD`가 들어 있어
로컬 파일로 덮으면 DB 접속이 끊긴다. 실제로 배포 전 키 이름을 비교해 이 차이를 확인했다.

## 2. 자동화 테스트 (pytest, 63개)

외부 LLM은 호출하지 않고 `monkeypatch`로 대체한다. 응답이 매번 달라 회귀 테스트로 쓸 수 없고
(같은 모델이 2.8초 → 60초 타임아웃으로 급변한 실측이 있다), 여기서 고정해야 할 것은 모델의
문장력이 아니라 **우리 코드의 계약**이기 때문이다. DB는 실제 Postgres를 쓰고, 테스트가
건드린 `anomaly_narrations` 행은 끝나면 원래대로 되돌린다.

| 그룹 | 개수 | 검증 내용 |
|---|---:|---|
| `TestVerifyNumbers` | 18 | 추적 가능한 값 통과(인용·단위환산·차이·시각·안내사항) / 지어낸 값 검출 / 반올림 허용오차 / 작은 임계값 인용·분→시간 환산 오탐 방지(2026-09-10) |
| `TestPromptPayload` | 4 | datetime·Decimal 직렬화, 긴 소수 반올림, 규칙 코드→조문 문장 변환, 참고 안내사항 포함 |
| `TestNarrateEvent` | 3 | 숫자 검증 실패 시 다음 모델로 넘어감 / 전부 실패 시 `NarrationUnavailable` / 키 없음과 모델 실패 구분 |
| `TestAnalysisFlow` | 11 | 요청 → `pending` → 백그라운드 생성 → DB 저장 → `done` / 저장본은 AI 재호출 없이 즉시 반환 / 상태 조회는 생성을 시작하지 않음 / AI 실패·키 없음은 HTTP 에러가 아닌 `failed`+안내문 / 실패 후 재요청 / 진행 중 중복 요청은 작업 1개 / 오래된 `pending` 재시작 / 주의 등급 신고초안 null / 클라이언트 수치 무시 |
| `TestNotFound` | 2 | 없는 이벤트는 두 엔드포인트 모두 404(유일한 HTTP 오류) |
| 기존 스위트 | 25 | 안전감지 스냅샷 10 + 영업상태/혼잡도 15 |

특히 마지막 항목(`test_client_supplied_values_are_ignored`)은 설계 의도를 고정한다 —
body에 `metric_value: 99999`를 끼워 넣어도 응답 근거 수치는 DB 값(45.0kW 등)이어야 한다.

## 4. 환각 검증기 — 실제로 잡은 사례

**배포 직후 첫 프로덕션 호출에서 검증기가 실제로 발동했다.**

```
verification_passed: false
unknown_numbers: ["58.5"]
```

모델이 관리자용 문장에 "계약전력 45kW의 130%인 **58.5kW**"라고 썼는데, 이 숫자는 입력에
없었다. 확인 결과 **환각이 아니라 단위 환산**이었다 — 임계값 14.625kWh(15분) × 4 = 58.5kW.
KEC는 kW로 규정하는데 우리 임계값은 15분 kWh로 저장돼 있어 모델이 자연스럽게 환산한 것이다.

추적 가능한 값이므로 허용 집합에 다음을 추가했다(커밋 `abb4eed`):
- 15분 kWh ↔ kW 환산(×4)
- 계약전력 × 규칙 비율 (45 × 130% = 58.5)

**허용 범위를 넓히면서 잡아야 할 것을 놓치지 않는지 재확인**:

| 문장 | 판정 |
|---|---|
| 관측 18.95kWh, 임계 14.62kWh, 계약전력 45kW | 통과 |
| KEC 212.3 기준 130%가 60분 지속 | 통과 |
| 임계치 14.62kWh는 순간전력 58.5kW에 해당 | 통과(환산) |
| 임계보다 4.32kWh 높습니다 | 통과(차이) |
| 내부 온도가 78도까지 상승했습니다 | **검출 `78`** |
| 관측 25.7kWh를 기록했습니다 | **검출 `25.7`** |
| 예상 피해액 350만원 | **검출 `350`** |
| 지난 3일간 12회 반복되었습니다 | **검출 `3`, `12`** |

이 사례가 이 계층을 채택한 근거를 그대로 보여준다 — **탐지 성능은 라벨이 없어 검증할 수
없었지만(AI_필요성_검증_결과.md), 설명 계층은 출력이 맞는지 기계가 매번 확인할 수 있다.**

## 5. 한계

1. **문장 품질은 사람이 읽고 판단했다.** 수치 정확성만 자동 검증되고, 문체·어조·적절성에는
   점수 체계가 없다.
2. **검증기는 "숫자"만 본다.** 잘못된 인과("냉장고 고장으로 보입니다")나 과장된 표현은
   시스템 프롬프트로만 억제하고 있고 자동 검출 대상이 아니다.
3. **응답이 3.8~11초로 느리다.** 화면에서는 로딩 표시가 필요하다. 외부 호스팅 모델 특성상
   더 느려질 수 있으며, 실제로 실험 중 같은 모델이 60초 타임아웃을 낸 적이 있다.
4. ~~캐시 폴백은 사전 생성된 이벤트에만 유효하다.~~ **(2026-09-10 해소)** 이 한계가 실제로
   운영 502로 터졌다. 캐시 폴백을 없애고, 분석은 사용자가 요청할 때 서버 백그라운드에서 만들어
   DB(`anomaly_narrations`)에 저장하도록 바꿨다. 외부 모델이 죽어도 이제 502가 아니라
   `status='failed'` + 재요청 안내가 간다. 경위는 `LLM_모델선정_비교실험.md` 6절.
5. **비용·쿼터를 계량하지 않았다.** 무료 티어 한도 초과 시 429가 나면 예비 키로 한 번 더
   시도한다. 두 키가 모두 소진되면 새 분석 요청은 failed 안내로 끝나지만, 이미 저장된 분석은
   DB에서 계속 읽힌다.
