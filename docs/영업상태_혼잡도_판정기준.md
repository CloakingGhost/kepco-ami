## 1. `final_status` — 4개 값의 판정 기준

### 1-1. 입력이 되는 두 하위 판정

**`schedule_status`** (`open_hours` \| `closed_hours`)
- 소스: `store_operating_hours`(`source='google_places'` 실측 우선, 없으면 `'ksic_estimate'` 추정)
- 코드: `db/src/ami_db/status.py`의 `determine_schedule_status()`(스칼라) / `db/scripts/09_compute_operating_status.py`의 `compute_status_for_store()`(벡터화 배치)
- 규칙: 조회 시각이 그 요일의 `[open_time, close_time]` 안이면 `open_hours`. `is_24h=true`면 항상 `open_hours`. `is_closed=true`이거나 시간 정보 자체가 없으면 `closed_hours`(정보 없음은 안전하게 닫힘 취급). `close_time < open_time`이면 자정을 넘기는 영업(예: 17:00\~익일 04:00)으로 간주해 "open 이후이거나 close 이전"으로 판정.

**`power_status`** (`active` \| `low`)
- 소스: `meter_timeseries.received_active_power_kwh`(해당 슬롯의 실측값, 또는 원천이 1시간 적산인 계기는 그 적산값을 15분 구간으로 분해한 값 — `SCHEMA.md`의 "data_resolution/is_redistributed" 절)
- 코드: `db/src/ami_db/status.py`의 `determine_power_status()` / 09단계 벡터화 버전
- 공식:
  ```
  night_baseline = median(그 계기의 0\~5시 recv_kWh, 실측 91일치)
  floor = max(night_baseline, 0.01)
  power_status = "active"  if recv_kWh >= floor × 1.5
               = "low"     if recv_kWh <  floor × 1.5   또는 recv_kWh가 NULL
  ```
  `1.5`(`ACTIVE_RATIO_THRESHOLD`)는 야간 대비 몇 배부터 "가동 중"으로 볼지의 배수. NULL을 무조건 `low`로 방어 처리하는 이유: 결측을 `active`로 잘못 판단하는 것보다 안전한 쪽으로 치우치기 위함.
- `data_resolution='1hour'`인 계기는 결측이 "가끔"이 아니라 슬롯의 75%가 구조적으로 없으므로, 이 low-방어 규칙을 적용하지 않고 그 슬롯의 판정 자체를 만들지 않는다(09단계 `data_resolution` 분기). 현재는 해당 계기가 없다 — 원천이 1시간 적산인 5개 계기(A-L-16/19/49/58/70)도 02단계가 15분 구간으로 분해해 적재하므로 전부 `15min`이다(`SCHEMA.md`의 "data_resolution/is_redistributed" 절).

### 1-2. 2×2 매트릭스 (코드: `status.FINAL_STATUS_MATRIX`)

| `schedule_status` \ `power_status` | `active` | `low` |
|---|---|---|
| `open_hours` | **영업중** | **휴무추정** |
| `closed_hours` | **예외영업** | **영업종료** |

### 1-3. 각 값의 실측 빈도 (267,582행 기준)

| 값 | 행 수 | 비율 | 의미 |
|---|---:|---:|---|
| 영업종료 | 89,869 | 33.59% | 영업시간표 밖 + 전력 낮음 — 가장 흔한 정상 케이스(심야 등) |
| 영업중 | 81,726 | 30.54% | 영업시간표 안 + 전력 정상 |
| 휴무추정 | 57,476 | 21.48% | 영업시간표상 열려있어야 하는데 전력이 야간 수준 |
| 예외영업 | 38,511 | 14.39% | 영업시간표상 닫혀있어야 하는데 전력이 야간 대비 1.5배 이상 |

### 1-4. "휴무추정" vs "예외영업" — 무엇이 다른가

| | 휴무추정 | 예외영업 |
|---|---|---|
| `schedule_status` | `open_hours`(표상 열려있어야 함) | `closed_hours`(표상 닫혀있어야 함) |
| `power_status` | `low`(전력 낮음) | `active`(전력 높음) |
| 어긋나는 방향 | 열려있어야 하는데 조용함 | 닫혀있어야 하는데 활발함 |
| 원문 근거 | `data/프로젝트개요.md` 원문이 명시한 유일한 케이스("영업중 전력량이 영업종료 시간과 같을시 영업 종료로 판단") | 원문에 명시적 언급 없음 — 코드 주석 "심야영업 등(관리자 알림 후보)"이 유일 근거 |

**휴무추정은 원문이 요구한 핵심 기능이라 설계 의도가 명확**하지만, **예외영업은 원문에 없는, 구현 과정에서 매트릭스의 나머지 한 칸을 채우려고 추가된 값**이라는 점이 근본적으로 다르다.

### 1-5. "예외영업"의 리스크 — 실측으로 확인된 문제

**빈도 자체가 "가끔"이 아니다.** 전체 슬롯의 14.39%(38,511행)로, `영업중`(30.54%)의 절반 가까이 된다. "심야영업 등 드문 예외"라는 이름의 함의와 실제 발생 빈도가 맞지 않는다.

**시간대별로 쪼개보면 "심야영업"이 지배적 원인이 아니다:**

| 시간대 | 예외영업 건수 | 비율 |
|---|---:|---:|
| 07\~10시 | 20,953 | 54.4% |
| 22\~23시(원래 의도한 "심야영업") | 3,460 | 9.0% |
| 나머지(0\~6, 11\~21시) | 14,098 | 36.6% |

**54.4%가 07\~10시에 몰려있다.** 이 시간대는 대부분 매장의 영업시작 추정시각 이전이다 — 즉 "심야영업"이 아니라 **영업 준비시간(재료 손질·예열·청소 등으로 야간보다 전력은 높지만 아직 개점 전인 상태)**이 지배적 원인으로 추정된다. 원래 이 값이 잡으려던 "22\~23시대 심야영업" 케이스는 오히려 9.0%로 소수다.

**운영시간 정보의 정밀도(구글 실측 vs KSIC 추정) 문제가 아니다** — 예외영업 최다 발생 매장(마티니 7,383건, 25센치꼬치앤오뎅바 3,323건 등) 상당수가 `google_places` 실측 운영시간을 쓰는 매장이다. 즉 "운영시간을 더 정확히 알면 해결된다"가 아니라, **`active_ratio_threshold=1.5`가 아침 준비시간대의 전력 상승을 걸러내지 못하는 임계값 설계 자체의 한계**로 판단된다.

**결론 — 이 값을 그대로 관리자 알림(2순위, 아직 미구현)의 트리거로 쓰면 안 된다.** 지금 코드에 이 완화 로직은 없다. `serving_api.py`의 `/api/anomalies`가 "영업종료 이후"만 필터링해 안전감지(2순위)는 이미 부분적으로 회피하고 있지만, `final_status='예외영업'` 라벨 자체는 여전히 넓게(전체의 14%) 잡히므로 이 필드를 그대로 사람에게 보여주거나 알림에 쓰면 아침 준비시간을 심야영업으로 오인시킬 위험이 크다.

**코드 위치**: `db/src/ami_db/status.py`(`determine_schedule_status`/`determine_power_status`/`FINAL_STATUS_MATRIX`), `db/scripts/09_compute_operating_status.py`(`compute_status_for_store`).

## 2. `congestion_level` — 3개 값의 판정 기준

### 2-1. 공식

혼잡도는 계약전력이 아니라 **그 매장 자신의 동시간대 분포**를 기준으로 삼는다:

```
congestion_level = "하"   if received_active_power_kwh ≤ Q1(동시간대)
                  = "중"   if Q1(동시간대) < received_active_power_kwh ≤ Q3(동시간대)
                  = "상"   if received_active_power_kwh > Q3(동시간대)
                  = NULL   if final_status ≠ "영업중"   (영업중이 아니면 혼잡도 자체가 무의미)
```

Q1/Q3는 "그 매장의 · 그 시각(±30분) · 최근 실측 30일" 표본에서 뽑은 **원본 kWh**(％로 정규화하지 않음) 사분위다.

### 2-2. 모집단 구성 — "동시간대 · 최근 30일 · 실측만"

| 축 | 값 | 이유 |
|---|---|---|
| 시간대 | ±30분(15분 슬롯 기준 앞뒤 2개씩, 총 5개 슬롯 묶음) | 정확히 같은 시:분만 모으면 하루 1개×30일=30개뿐이라 사분위가 노이즈에 민감해진다. 요일 구분은 하지 않는다(요일까지 쪼개면 슬롯당 표본이 ~4개로 더 줄어 오히려 못 믿을 값이 됨). |
| 기간 | 최근 30일(그 매장 실측 범위 안에서) | 계절성을 고려하면 3개월이 이상적이나 실측 데이터가 91일(2026-04-01~06-30)뿐이라 1개월로 타협. |
| 실측/합성 | 실측(`is_synthetic=false`)만 | 합성 7월은 안전감지 데모용으로 위험/주의 이상치가 일부러 심긴 구간이라, 기준 산정에 섞으면 기준 자체가 오염된다. |
| 영업상태 | `final_status='영업중'`만 | 혼잡도는 영업 중일 때만 의미 있는 값이므로 그 모집단에서만 사분위를 잡아야 한다(예전 방식과 같은 원칙 — 하루 전체로 잡으면 '하'가 사라지는 문제가 있었음). |

표본이 5개 미만인 시간대(운영 시작 초기라 특정 슬롯만 표본이 유독 적은 경우 등)는 그 시간대만의 기준을 못 믿고, 그 매장의 "시간대 구분 없는 전체" Q1/Q3로 폴백한다.

**코드 위치**: `db/src/ami_db/status.py`의 `compute_congestion_thresholds()`, `db/scripts/09_compute_operating_status.py`의 `compute_status_for_store()`.

### 2-3. 왜 바꿨는가 — 계약전력 방식의 두 가지 문제 (2026-09-11 개정)

기존 방식(`compute_utilization_quartiles`, 삭제됨)은 계약전력 대비 이용률(%)을 매장의 **영업시간 전체를 한 덩어리**로 사분위 처리했다. `db/problem/문제상황-1.txt`가 지적한 문제:

1. **시간대 구분이 없었다.** 개점 직후 한산한 시간과 점심 피크가 같은 Q1/Q3 기준에 뭉뚱그려져, "이 시간대엔 항상 한산하다/바쁘다"는 매장별 패턴이 반영되지 않았다.
2. **계약전력 대비 %라는 척도 자체가 "혼잡도"의 목적과 안 맞았다.** 계약전력은 "과부하 위험에 얼마나 가까운가"를 보는 안전감지(`ami_db.anomaly`)의 척도지, 사용자 화면이 보여주려는 "평소보다 붐비는가"와는 다른 질문이다. 계기별 계약전력이 3~45kW로 15배 차이 나는 것도 매장마다 사분위 구간 폭을 왜곡시켰다.

**부수적으로 개선된 문제**: 계약전력 대비 %는 저사용 매장(예: 명랑핫도그화곡중앙, 계약전력 3kW인데 실사용은 1%도 안 씀)에서 Q1≈Q3로 사실상 붕괴하는 퇴화 사례가 있었다(구 2-5절, IQR 0.19%p — 아래 2-5절 참고). 원본 kWh로 바꾸자 이 매장도 시간대별 IQR이 절대 스케일에 맞게 넓어졌다(예: 14:00 슬롯 Q1=0.018kWh/Q3=0.036kWh, 상대IQR 100%) — 다만 이건 겨냥한 목표가 아니라 계약전력 정규화를 없앤 데 따른 부수 효과다.

### 2-4. 참고 — 시간대별로 기준이 달라지는 예시 (2026-09-11 재계산)

같은 매장 안에서도 시간대별로 Q1/Q3가 서로 다르다: `store_id=7`(명랑핫도그화곡중앙, A-L-37)은 14:00엔 Q1=0.018kWh/Q3=0.036kWh, 15:00엔 Q1=0.016kWh/Q3=0.025kWh로 경계 자체가 시간에 따라 이동한다. 전 매장 96슬롯 전체를 표로 박제하지는 않는다 — 최근 30일 창을 쓰므로 재실행할 때마다 값이 바뀌고, 재현은 아래 명령으로 언제든 가능하기 때문이다.

```python
# 특정 매장의 (시간대→Q1/Q3) 딕셔너리를 직접 보고 싶으면:
from ami_db.status import compute_congestion_thresholds
thresholds, fallback = compute_congestion_thresholds(real_open)  # real_open: 실측+영업중 ts/recv_kWh 두 컬럼
```

Q1/Q3 자체는 DB에 저장되지 않는다(계산 즉시 판정에만 쓰고 버린다 — `night_baseline`과 같은 패턴).

> ⚠ 상호명은 이후에도 Google Places 재매칭이 계속 실행되므로(`db/scripts/12~17_*.py`) 이 문서보다 `stores` 테이블이 항상 최신이다.

### 2-5. 알려진 통계적 약점 — 잔존 퇴화(degenerate) 리스크

`IQR = Q3 − Q1`이 그 시간대 값 자체에 비해 아주 작으면 "중" 구간이 사실상 존재하지 않아 작은 변동에도 "상"↔"하"가 튈 수 있다. 2026-09-11 재계산 기준 21개 매장 전체를 스캔한 결과, 상대IQR(=IQR÷중앙값) 최솟값은 매장별로 2.7%\~32.9% 범위였다 — 예전에 유일하게 퇴화 사례로 지목됐던 `A-L-37`(명랑핫도그화곡중앙)은 최소 6.5%까지 개선됐지만, 다른 매장(예: 유림다방 2.7%) 중 일부 시간대는 여전히 상대적으로 좁은 구간이 남아 있다.

**이 문서의 이전 버전(2026-09-03)이 제안했던 "고정 배율 밴드(`[median×0.7, median×1.3]`)로 폴백"은 여전히 코드화되지 않았다.** 표본 부족 시(2-2절) 매장 전체로 폴백하는 안전장치는 있지만, "표본은 충분한데 그 시간대 값 자체가 평평한" 케이스에 대한 별도 폴백은 없다.
